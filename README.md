# Bank Transfer API

A REST API for managing bank customers and accounts, built with Spring Boot. It supports deposits, withdrawals and money transfers between accounts. The focus is on correctness: concurrent balance updates, atomic transfers and consistent error handling.

## Tech Stack

- Java 21
- Spring Boot (Spring Web, Spring Data JPA / Hibernate, Bean Validation)
- MySQL
- springdoc-openapi (Swagger UI)
- Maven

## Key Design Decisions

**Pessimistic locking for balance updates**
Every operation that changes a balance first reads the account with `SELECT ... FOR UPDATE` (`@Lock(PESSIMISTIC_WRITE)`). Concurrent requests on the same account wait for each other instead of overwriting each other's updates (no lost updates). I chose pessimistic over optimistic locking because concurrent requests on the same account are a realistic case in banking, and waiting is more predictable for the client than failing and retrying.

**Deadlock prevention with ordered locking**
A transfer locks two accounts. If transfer A→B and transfer B→A run at the same time and each locks its source account first, they can end up waiting on each other forever. To prevent this, both accounts are always locked in the same order (smaller account number first), regardless of the transfer direction. A request that holds the second lock has always acquired the first one already, so a circular wait cannot form.

**Atomic transfers**
A transfer runs in a single `@Transactional` method: both locks, both balance changes and the transaction record. If any step fails (e.g. insufficient balance), everything is rolled back. No balance changes and no record is written.

**Rich domain model**
Balance rules live in the `Account` entity (`deposit`, `withdraw`). There is no `setBalance`, so a balance can only change through these methods. Every balance change produces an immutable `Transaction` record (`DEPOSIT`, `WITHDRAW` or `TRANSFER`). A transfer produces a single `TRANSFER` record with both the source and target accounts.

**Money as `BigDecimal`**
Amounts are stored as `DECIMAL(19, 2)` and compared with `compareTo`, never with `equals` or floating-point types.

**DTOs and validation**
Entities are never exposed by controllers. Requests and responses are Java records. Validation is split by responsibility:
- Format rules (required fields, positive amount, max 2 decimal places): Bean Validation on request DTOs
- Rules that need system state (email already used, currency mismatch): service layer
- Balance rules: entity, as the last line of defense

**Consistent error handling**
A single `@RestControllerAdvice` maps every exception to the same JSON error format with a machine-readable `errorCode`. HTTP status codes are chosen deliberately:
- `400`: the request itself is invalid (validation, malformed body, transfer to the same account)
- `404`: resource not found
- `409`: conflict with existing data
- `422`: the request is valid, but the current state does not allow it (insufficient balance, currency mismatch)

Internal details (e.g. Jackson parser messages) are never leaked to the client.

## Getting Started

### Prerequisites
- Java 21+
- MySQL 8+

### 1. Create the database
```sql
CREATE DATABASE bank_db;
```
Tables are created automatically on startup.

### 2. Set environment variables
```bash
export DB_USERNAME=your_mysql_username
export DB_PASSWORD=your_mysql_password
```

### 3. Run
```bash
./mvnw spring-boot:run
```

### 4. Open Swagger UI
http://localhost:8080/swagger-ui/index.html

## API Endpoints

| Method | Path | Description | Success |
|---|---|---|---|
| `POST` | `/api/customers` | Create a customer | `201` |
| `GET` | `/api/customers/{customerId}` | Get a customer | `200` |
| `POST` | `/api/accounts` | Open an account (TRY or USD) | `201` |
| `GET` | `/api/accounts/{accountNumber}` | Get an account | `200` |
| `POST` | `/api/accounts/{accountNumber}/deposit` | Deposit money | `200` |
| `POST` | `/api/accounts/{accountNumber}/withdraw` | Withdraw money | `200` |
| `POST` | `/api/transfers` | Transfer money between accounts | `201` |

Account numbers are generated by the system (10 digits). Accounts open with a zero balance.

## Example Requests

### Transfer
`POST /api/transfers`
```json
{
  "fromAccountNumber": "4821937560",
  "toAccountNumber": "7139204856",
  "amount": 250.00
}
```

Response `201 Created`:
```json
{
  "id": 7,
  "type": "TRANSFER",
  "amount": 250.00,
  "fromAccountNumber": "4821937560",
  "toAccountNumber": "7139204856",
  "createdAt": "2026-11-08T19:02:41.512"
}
```

### Error: insufficient balance
Response `422 Unprocessable Content`:
```json
{
  "errorCode": "INSUFFICIENT_BALANCE",
  "message": "Insufficient balance",
  "timestamp": "2026-11-08T16:03:10.284Z"
}
```

## Error Codes

| Error Code | Status | When |
|---|---|---|
| `VALIDATION_FAILED` | `400` | Request fields are invalid (details in `fieldErrors`) |
| `MALFORMED_REQUEST` | `400` | Body is missing, not valid JSON, or has an unknown enum value |
| `INVALID_AMOUNT` | `400` | Amount is missing, zero or negative |
| `SAME_ACCOUNT_TRANSFER` | `400` | Source and target accounts are the same |
| `CUSTOMER_NOT_FOUND` | `404` | Customer does not exist |
| `ACCOUNT_NOT_FOUND` | `404` | Account does not exist |
| `EMAIL_ALREADY_EXISTS` | `409` | Email is already registered |
| `DATA_INTEGRITY_VIOLATION` | `409` | Request conflicts with existing data |
| `INSUFFICIENT_BALANCE` | `422` | Balance is lower than the requested amount |
| `CURRENCY_MISMATCH` | `422` | Accounts have different currencies |
